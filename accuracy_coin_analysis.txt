--- FAIL 1: Page 12, Test 1 — "Interrupt flag latency" ---
  Kod błędu: A
  Komunikat: "Branch instructions should not poll for interrupts before cycle 3."

  OPIS TESTU (TEST_IFlagLatency, test A, linia ~9657):
    Test sprawdza, czy rozgałęzienia (branch) NIE odpytują o przerwania
    przed cyklem 3. Konkretnie: branch NOT taken (BNE po LDA <ErrorCode,
    gdzie ErrorCode != 0, więc branch JEST taken — ale test sprawdza, że
    IRQ nie zostanie wykryte w cyklu 3 brancha, tylko w następnej instrukcji).

    Scenariusz:
    - IRQ level detector zostaje ustawiony w trakcie wykonywania brancha
      (między cyklem 2 a 3).
    - Branch nie powinien odpytywać o przerwania po cyklu 3 (gdy branch
      nie przekracza strony — polluje tylko raz przed cyklem 2).
    - IRQ powinno nastąpić dopiero po następnej instrukcji (INX).

  [P] CPU6502::am_rel_1() wywołuje pollInterrupts() gdy wykryje page cross,
      ale dla branch NOT crossing page nie ma dodatkowego polla — to jest OK.
      Problem może być w tym, że opFetch() (cykl 1 nowej instrukcji) polluje
      przerwania, a branch powinien pollować TYLKO przed cyklem 2 (czyli
      w am_rel_1). Jeśli CPU polluje w cyklu 1 brancha (opFetch przed
      decodeAndDispatch), to może wykryć IRQ za wcześnie.

      Patrz: clockPhi1() ustawia nmiPollSignal/irqDetected, a opFetch()
      wywołuje pollInterrupts(). To znaczy że poll występuje w cyklu 1
      każdej instrukcji (włącznie z branchami). Zgodnie z komentarzem w
      teście: "A branch that isn't taken only polls once before the second
      cycle, while a branch that is taken additionally polls right before
      the fourth cycle."

      Aktualny kod: opFetch() polluje w cyklu 1 (przed decodeAndDispatch).
      To jest poll "przed cyklem 2" — poprawne dla brancha.
      ALE: am_rel_1() jest wywoływane w cyklu 2 (po fetchu operandu).
      Jeśli branch jest taken i nie crossuje strony, am_rel_2_taken()
      wraca do opFetch() — co powoduje poll w cyklu 3. To jest poll
      "przed cyklem 4" — ale test mówi że branch NOT crossing page
      powinien pollować TYLKO przed cyklem 2, NIE przed cyklem 3.

  [F] Dla branch taken nie crossującego strony, am_rel_2_taken() powinno
      wrócić bezpośrednio do opFetch(), ale opFetch() nie powinien pollować
      przerwań w tym cyklu — to jest cykl 3 brancha, a poll powinien być
      tylko przed cyklem 2 i (dla branch crossing page) przed cyklem 4.

      Problem strukturalny: opFetch() zawsze polluje. Trzeba rozróżnić
      "poll w cyklu 1 nowej instrukcji" od "poll w cyklu 3 brancha".
      Może dodać flagę "skipPoll" lub restrukturować branch timing.

  [R] Zmiana pollowania przerwań wpłynie na wszystkie testy CPU interrupts
      oraz na gry korzystające z precyzyjnego timingu NMI/IRQ.

--- FAIL 2: Page 12, Test 2 — "NMI Overlap BRK" ---
  Kod błędu: 2
  Komunikat: "Either NMI timing is off, or interrupt hijacking is incorrectly handled."

  OPIS TESTU (TEST_NmiAndBrk, linia ~9830):
    Test synchronizuje CPU tak, że NMI występuje na 8-A cykli przed VBlank.
    Następnie uruchamia BRK. Sprawdza "interrupt hijacking" — co się dzieje
    gdy NMI i BRK występują jednocześnie.

    BRK to instrukcja 7-cyklowa. NMI może "przejąć" (hijack) BRK w różnych
    momentach. Test sprawdza 16 różnych timingów (A=0..15) i porównuje
    z kluczem odpowiedzi (answer key).

    Klucz odpowiedzi zawiera wartości $A5, $A4, $35, $34, $25, $24, $00.
    Wartości te reprezentują różne stany: czy BRK pominął bajt, czy NMI
    przejął wektor, jakie flagi zostały zapisane na stosie.

  [P] Interrupt hijacking w CPU6502::int3_pushPCL() (linia 581):
      Kod sprawdza nmiEdgeDetected w trakcie push PCL. Jeśli NMI zostało
      wykryte, currentInt zmienia się na NMI. Ale to działa tylko dla
      BRK→NMI hijacking w jednym konkretnym momencie.

      Problem może być w timingie detekcji NMI:
      - nmiPending jest ustawiane w clockPhi2() gdy wykryto edge.
      - nmiEdgeDetected jest ustawiane w clockPhi1() (jako snapshot).
      - nmiPollSignal = nmiEdgeDetected (poprzedni cykl).
      - pollInterrupts() używa nmiPollSignal.

      To oznacza 1 cykl opóźnienia między edge a poll. Ale test wymaga
      precyzyjnego timingu — NMI musi być wykryte w odpowiednim cyklu BRK.

      Dodatkowo: int1_dummy() inkrementuje PC dla BRK (PC++), ale jeśli
      NMI przejmuje, PC nie powinien być inkrementowane. Aktualny kod
      robi PC++ w int1_dummy() ZANIM sprawdza hijacking w int3_pushPCL().
      To może być problem — jeśli NMI przejmuje, PC już został inkrementowane.

  [F] 1. Sprawdzić czy int1_dummy() powinno inkrementować PC tylko gdy
        currentInt == SoftwareBRK i NMI NIE przejmuje.
     2. Sprawdzić timing detekcji NMI edge — może być potrzebny dodatkowy
        poll w cyklu 3 lub 4 BRK (zgodnie z komentarzem w teście: "BRK seems
        to poll before cycle 2, 3, 4, and 5").
     3. Hijacking powinien być sprawdzany w int3_pushPCL() — ale może też
        w int1_dummy() lub int2_pushPCH().

  [R] Zmiana hijackingu wpłynie na FAIL 3 (NMI Overlap IRQ) i potencjalnie
      na inne testy z przerwaniami.

--- FAIL 4: Page 13, Test 9 — "Explicit DMA Abort" ---
  Kod błędu: 2
  Komunikat: "The aborted DMAs did not spend the correct number of CPU cycles."

  OPIS TESTU (TEST_ExplicitDMAAbort, linia ~13190):
    Test wyłącza DMC ($4015 = 0) w trakcie trwania DMA i mierzy ile cykli
    CPU DMA zajęło. Answer key: $04 $04 $04 $04 $04 $04 $03 $04 $01 $01
    $00 $00 $00 $00 $00 $00.

    Wartości oznaczają liczbę cykli DMA:
    - $04 = normalny 4-cyklowy DMA (reload, halt on put)
    - $03 = 3-cyklowy DMA (load, halt on get, lub reload z opóźnieniem)
    - $01 = 1-cyklowy aborted DMA (tylko halt cycle)
    - $00 = DMA nie wystąpiło wcale

    Test sprawdza 16 różnych timingów wyłączenia DMC.

  [P] DMA::clockPhi1() — logika abortu w DMCPhase::Halt i DMCPhase::Dummy:
      - W Halt: jeśli !isDMCSampleNeeded(), dmcPhase = Idle (DMA nie wystąpi)
      - W Dummy: jeśli !isDMCSampleNeeded(), dmcPhase = Idle (1-cyklowy abort)
      - W Read: jeśli !isDMCSampleNeeded(), dmcPhase = Idle

      Problem: dmcHaltArmed — flaga "uzbrojenia" halt. Jeśli DMA jest
      "armed" ale nie jeszcze "halted", a potem DMC zostaje wyłączone,
      kod w Halt sprawdza isDMCSampleNeeded() i wraca do Idle. To jest OK.

      Ale: w DMCPhase::Dummy, jeśli DMC zostaje wyłączone, DMA kończy się
      po 1 cyklu (tylko halt). To daje $01. Ale answer key pokazuje $00
      dla ostatnich 6 przypadków — DMA nie wystąpiło wcale.

      Specyfikacja (dma.txt "Bugs"):
      "When sample playback is stopped during the APU cycle before a reload
      DMA would schedule (2nd or 3rd CPU cycle before the halt attempt),
      the DMA starts but is aborted after a single cycle. If the halt is
      delayed due to a write cycle, the aborted DMA doesn't occur at all."

      Kluczowe: "If the halt is delayed due to a write cycle, the aborted
      DMA doesn't occur at all." — to tłumaczy $00 dla niektórych przypadków.

  [F] 1. Sprawdzić czy DMA poprawnie obsługuje przypadek gdy halt jest
        opóźniony przez write cycle i DMC zostaje wyłączone — DMA nie
        powinno wystąpić wcale ($00).
     2. Sprawdzić czy dmcHaltArmed jest poprawnie resetowane gdy DMC
        zostaje wyłączone w fazie Halt.
     3. Obliczyć timing: dmc.dmaDelay = 3 po $4015 write. DMA próbuje
        halt po 2 APU cyklach. Jeśli DMC jest wyłączane w odpowiednim
        cyklu, DMA może być w różnych fazach.

  [R] Zmiany w DMA abort wpłyną na FAIL 5 (Implicit DMA Abort) i potencjalnie
      na testy DMC.

--- FAIL 5: Page 13, Test 10 — "Implicit DMA Abort" ---
  Kod błędu: 2
  Komunikat: "The aborted DMAs did not spend the correct number of CPU cycles."

  OPIS TESTU (TEST_ImplicitDMAAbort, linia ~13261):
    Test używa 1-bajtowego sample z looping disabled. Load DMA ładuje 1 bajt,
    potem buffer zostaje pusty i reload DMA jest schedulowane, ale sample
    już się skończył (bytesRemaining == 0), więc DMA jest aborted.

    Answer keys (3 pętle po 16 wyników):
    - Key1 ($500): normalne abort timing
    - Key2 ($520): z write cycle (JSR) — 1-cycle DMA nie występuje na write
    - Key3 ($540): z looping włączonym

    Komentarz w teście: "The 1-cycle DMA does not get delayed by a write
    cycle, instead it just doesn't occur at all."

  [P] Podobne jak FAIL 4, ale dotyczy implicit abort (gdy sample kończy się
    naturalnie, nie przez wyłączenie $4015).

      W DMCChannel::loadSampleBuffer(): gdy bytesRemaining == 0 i !loopFlag,
      irqPending = true (jeśli irqEnabled). Ale sampleBufferEmpty = false
      (właśnie załadowano). Potem gdy buffer zostaje opróżniony (clockTimer),
      sampleBufferEmpty = true i dmaHaltOnPut = true. needsDMAFetch() zwraca
      false bo bytesRemaining == 0.

      Problem: gdy bytesRemaining == 0, needsDMAFetch() zwraca false, więc
      DMA nigdy nie wystąpi. Ale specyfikacja mówi, że reload DMA jest
      schedulowane gdy buffer zostaje opróżniony — nawet jeśli sample się
      skończył, DMA jest aborted po 1 cyklu.

      Klucz: dmaHaltOnPut jest ustawiane w clockTimer() gdy buffer zostaje
      opróżniony. Ale needsDMAFetch() sprawdza bytesRemaining > 0, więc
      jeśli sample się skończył, DMA nie jest schedulowane.

      To jest BŁĄD: reload DMA powinno być schedulowane niezależnie od
      bytesRemaining — jest schedulowane gdy buffer zostaje opróżniony.
      Dopiero w trakcie DMA (w fazie Halt/Dummy/Read) sprawdzane jest
      czy sample nadal jest potrzebne.

  [F] 1. Rozdzielić "DMA requested" od "sample needed":
       - DMA powinno być schedulowane gdy sampleBufferEmpty && dmaHaltOnPut
         (buffer został opróżniony podczas playbacku).
       - needsDMAFetch() powinno zwracać true gdy buffer jest pusty i
         DMA zostało requested, NIE zależnie od bytesRemaining.
       - W DMA::clockPhi1(), w fazie Halt/Dummy/Read, sprawdzać
         isDMCSampleNeeded() — jeśli false, abort.
     2. Dodać flagę "dmaRequested" w DMCChannel, ustawianą gdy buffer
        zostaje opróżniony, czyszczoną gdy DMA zostanie zrealizowane
        lub aborted.

  [R] Zmiany wpłyną na FAIL 4, FAIL 6 (DMC), i potencjalnie na inne
      testy DMA. To jest znacząca zmiana w logice DMA.

--- FAIL 6: Page 14, Test 6 — "Delta Modulation Channel" ---
  Kod błędu: L
  Komunikat: "Writing $4015 when the DMC timer has 2 cycles until clocked
              should not trigger a DMC DMA until after the 3/4 cycle delay."

  OPIS TESTU (TEST_DeltaModulationChannel, test L, linia ~11300):
    Test sprawdza opóźnienie DMA po zapisie do $4015:
    - DMC timer ma 2 cykle do zera.
    - Zapis $10 do $4015 włącza DMC.
    - DMA powinno być opóźnione o 1 cykl (bo DMC nie jest jeszcze włączone
      gdy timer osiąga zero).
    - DMA powinno trwać 3 cykle zamiast 4 (bo jest alignment cycle).

    Scenariusz:
    1. DMASync_50CyclesRemaining — synchronizacja
    2. Wyłączenie DMC, ustawienie 1-bajtowego sample z loop
    3. Clockslide_25 — timer = 7
    4. STA $4015 — włączenie DMC z 2 cyklami do zera timera
    5. DMA powinno być opóźnione o 1 cykl (3 cykle zamiast 4)

  [P] APU::writeData() case 0x4015:
      Gdy data & 0x10 i bytesRemaining == 0:
        dmc.restart();
        dmc.dmaDelay = 3;

      dmaDelay = 3 oznacza 3 cykle opóźnienia. Ale test mówi że gdy timer
      ma 2 cykle do zera, DMA powinno być opóźnione o 1 cykl (bo DMC
      włącza się po 3 cyklach, a timer osiąga zero po 2 cyklach).

      Problem: dmaDelay = 3 to opóźnienie w APU cyklach. Ale DMC timer
      osiąga zero po 2 cyklach. Wtedy needsDMAFetch() sprawdza dmaDelay == 0
      — jeśli dmaDelay = 1 (po 2 cyklach), DMA nie wystąpi. Dobrze.

      Ale: gdy dmaDelay osiągnie 0 (po 3 cyklach), needsDMAFetch() zwraca
      true (jeśli sampleBufferEmpty && bytesRemaining > 0). W tym momencie
      DMA jest schedulowane jako "load" DMA (halt on get).

      Test oczekuje że DMA będzie 3-cyklowe (z alignment cycle) zamiast
      4-cyklowego. To zależy od tego czy halt występuje na get czy put.
      Load DMA haltuje na get → 3 cykle. To powinno działać.

      Problem może być w tym, że gdy timer osiąga zero PRZED włączeniem DMC,
      DMC próbuje schedulować reload DMA (gdy buffer zostaje opróżniony),
      ale DMC nie jest jeszcze włączone. To jest powiązane z FAIL 5.

      Dodatkowo: dmc.tickDMADelay() jest wywoływane w APU::clock(), ale
      dmaDelay jest ustawiane na 3. Po 3 cyklach APU (6 cyklach CPU? nie,
      1 APU cycle = 1 CPU cycle), dmaDelay = 0. Ale test mówi o 2 cyklach
      do zera timera — to znaczy że timer osiąga zero zanim dmaDelay = 0.

      Gdy timer osiąga zero, clockTimer() jest wywoływane. Jeśli to był
      ostatni bit w buforze, sampleBufferEmpty = true i dmaHaltOnPut = true.
      Ale needsDMAFetch() zwraca false bo dmaDelay > 0. Po 1 cyklu dmaDelay
      = 0 i needsDMAFetch() zwraca true. Ale dmaHaltOnPut = true (reload DMA),
      a nie false (load DMA). To jest problem — powinno być load DMA (halt
      on get), bo to jest DMA po $4015 write, nie reload.

  [F] 1. Gdy $4015 włącza DMC, dmaHaltOnPut powinno być ustawione na false
        (load DMA) w restart() — to już jest.
     2. Ale gdy timer osiąga zero i buffer zostaje opróżniony PRZED
        dmaDelay = 0, dmaHaltOnPut jest ustawiane na true (reload) w
        clockTimer(). To nadpisuje wartość false z restart().
     3. Rozwiązanie: gdy dmaDelay > 0, nie ustawiaj dmaHaltOnPut = true
        w clockTimer(), bo to nie jest reload DMA — to jest load DMA
        opóźnione przez dmaDelay.

  [R] Powiązane z FAIL 5. Zmiana w logice dmaHaltOnPut może wpłynąć na
      inne testy DMC.

--- FAIL 7: Page 14, Test 7 — "APU Register Activation" ---
  Kod błędu: 6
  Komunikat: "OAM DMA should be able to read from APU registers (and mirrors)
              if $40 is written to $4016 and the bus is $4000-$401F."

  OPIS TESTU (TEST_APURegActivation, test 6, linia ~8220):
    Test sprawdza czy OAM DMA może czytać z rejestrów APU gdy 6502 address
    bus jest w zakresie $4000-$401F.

    Scenariusz:
    1. Wykonaj STA $4014 (A=$40) z adresu $3FFE.
    2. 6502 address bus będzie $4001 gdy OAM DMA wystąpi.
    3. OAM DMA czyta z page $40 ($4000-$40FF).
    4. Ponieważ 6502 address bus jest w $4000-$401F, rejestry APU są aktywne.
    5. OAM DMA powinno czytać wartości z rejestrów APU ($4015, $4016, $4017)
       i ich mirrorów co $20 bajtów.

    Oczekiwane wyniki w OAM (patrz komentarz w teście, linia ~8251):
    - $4015 mirror → $44 (frame IRQ flag + triangle)
    - $4016 mirror → $01 (controller 1)
    - $4017 mirror → $00 (controller 2)
    - Pozostałe → open bus ($50 lub $40)

  [P] A2A03::readDMA() — logika aktywacji rejestrów APU:
      const bool regActive = (coreAddr >= 0x4000 && coreAddr <= 0x401F);
      To sprawdza czy 6502 core address jest w $4000-$401F.

      Ale: OAM DMA używa dma.getAddr() (adres OAM DMA), a coreAddr to
      cpu.getAddr() (adres CPU). Gdy OAM DMA jest aktywne, CPU jest halted
      i powtarza ostatni read cycle. coreAddr powinno być adresem instrukcji
      STA $4014, czyli $3FFE lub $3FFF... ale test celowo ustawia to tak,
      że 6502 address bus jest $4001.

      Problem: gdy OAM DMA czyta z $4015, kod w readDMA() sprawdza:
      if (regActive && reg == 0x4015) — to powinno działać.
      Ale OAM DMA nie używa readDMA() — to jest tylko dla DMC DMA!

      OAM DMA używa dmaReadData() → readData() → ale readData() sprawdza
      dma.overridesAddr(). Dla OAM DMA, dma.overridesAddr() zwraca true
      (action != None). Więc readData() wywołuje readDMA().

      W readDMA(): regActive sprawdza coreAddr (cpu.getAddr()). Dla OAM DMA,
      cpu.getAddr() zwraca currentStep.busAddr — ale CPU jest stalled,
      więc currentStep nie jest aktualizowane. currentStep.busAddr to
      adres ostatniego read cycle CPU, czyli adres instrukcji.

      Test wykonuje STA $4014 z $3FFE. Po STA $4014, CPU wykonuje read
      cycle (następna instrukcja). Ale OAM DMA haltuje CPU na tym read cycle.
      Adres tego read cycle to $4000 lub $4001 (następna instrukcja po
      STA $4014 z $3FFE).

      Problem: cpu.getAddr() zwraca currentStep.busAddr, ale gdy CPU jest
      stalled (RDY low), currentStep nie jest aktualizowane — zatrzymuje się
      na ostatnim adresie. To może być $3FFF lub $4000, zależnie od timingu.

      Test wymaga aby 6502 address bus był $4001. Jeśli CPU jest stalled
      na read cycle z adresu $4001, to coreAddr = $4001 i regActive = true.

      Ale: OAM DMA w DMA::clockPhi1() używa idma.pollIsRead() (cpu.isRead()).
      Gdy OAM DMA jest w fazie Transfer, CPU jest halted (rdy = false).
      cpu.isRead() zwraca currentStep.isRead. Jeśli CPU był w read cycle
      gdy zostało zhaltowane, isRead = true.

      Kluczowy problem: readDMA() dla OAM DMA get używa dmaAddr (adres OAM
      DMA = $40xx), ale regActive sprawdza coreAddr (adres CPU). Jeśli
      coreAddr = $4001, to regActive = true. Ale readDMA() czyta z
      readExternal(dmaAddr) — dmaAddr = $40xx. readExternal() sprawdza:
      if (addr >= 0x4000 && addr <= 0x401F) return busData;
      To zwraca busData (open bus) zamiast czytać rejestr APU!

      Dla OAM DMA czytającego $4015, $4016, $4017:
      - dmaAddr = $4015, $4016, $4017
      - readExternal($4015) → return busData (bo $4015 w $4000-$401F)
      - Ale powinno czytać rejestr APU!

      readDMA() ma specjalną logikę dla reg == 0x4015 i reg == 0x4016/4017,
      ale tylko dla DMC DMA (dma.actionIsDMCGet()). OAM DMA (OAMGet) nie
      ma tej logiki.

  [F] 1. W readDMA(), dodać obsługę OAM DMA dla rejestrów APU:
       - Jeśli regActive i reg == 0x4015, czytaj $4015 z APU.
       - Jeśli regActive i reg == 0x4016/4017, czytaj controller.
       - To powinno działać dla OAMGet tak samo jak dla DMCGet.
     2. Usunąć warunek dma.actionIsDMCGet() — logika aktywacji rejestrów
        powinna działać dla każdego DMA, nie tylko DMC.

  [R] Zmiana wpłynie na testy DMA + $4015 Read, DMA + $4016 Read (obecnie
      PASS) — trzeba uważać, żeby ich nie zepsuć.

--- FAIL 8: Page 18, Test 3 — "$2002 flag timing" ---
  Kod błędu: 1
  Komunikat: "The flags were not cleared on the correct PPU cycle."

  OPIS TESTU (TEST_2002FlagTiming, linia ~2263):
    Test czyta $2002 w różnych momentach pre-render scanline i sprawdza
    kiedy flagi sprite_zero_hit i sprite_overflow są czyszczone.

    Klucz: Wszystkie flagi ($2002 bit 7, 6, 5) są czyszczone na dot 1
